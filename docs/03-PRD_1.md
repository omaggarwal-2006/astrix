# 03 · Product Requirements Document (PRD)

Version 1.0 · Status: Draft for hackathon build · Owner: Raghav (with Tanishk, Om)

## 1. Purpose
Define what LANDFALL must do so a deep-space crew member can evaluate and act on their health with delayed or no contact with Earth.

## 2. Goals
- G1. Detect meaningful drift from each astronaut's **own** baseline and explain it.
- G2. Forecast landing-day readiness and show the effect of exercise adherence.
- G3. Recommend the right responder (self / CMO / flight surgeon) given comm delay.
- G4. Produce a verifiable report packet that survives link loss.
- G5. Run fully offline in a browser with zero setup.

## 3. Non-goals
- Real diagnosis, treatment advice or regulatory-grade medical software.
- Real telemetry integration, real networking, multi-user accounts, a backend.
- Radiation dosimetry modelling (mentioned as future work only).

## 4. Personas
| Persona | Need | Success |
|---|---|---|
| Astronaut (e.g., crew member on Mars transit) | Understand own status, know what to do | Reads the status card and the proposed action in <10 s |
| Crew Medical Officer | Prioritized, explained case | Sees flags, rationale, trend context |
| Flight surgeon | Compact verifiable report | Receives packet with checksum, trends and baseline summary |

## 5. User stories
1. As an astronaut I see today's metrics versus my baseline so I know what changed.
2. As an astronaut I see *why* an alert fired (metric, size of deviation, persistence, trend).
3. As an astronaut I move an exercise slider and see predicted landing-day bone/strength/aerobic effect.
4. As an astronaut I see the current one-way delay and which responder is recommended.
5. As a CMO I see a rationale and the proposed action for the case.
6. As an astronaut with an emergency indicator I am told to use the direct ground link immediately, regardless of queue state.
7. As an astronaut I can send a report that is queued if the link is down, retried on failure, and shown as acknowledged when the (simulated) ground replies.
8. As a reviewer I can see all sources and which numbers are NASA figures vs team assumptions.

## 4+. Functional requirements

### FR-A Data and baseline (Tanishk)
- FR-A1 Synthetic 180-day dataset for each astronaut: sleep hours, mood (1–5), heart rate, cabin CO2, symptoms, immune markers.
- FR-A2 Baseline computed from early-mission window; per-metric mean/SD.
- FR-A3 Drift detection via z-score plus persistence (days) and worsening trend; CUSUM/EWMA permitted.
- FR-A4 Each alert returns metric, severity, reason text, persistedDays, worsening.

### FR-B Forecast (Tanishk)
- FR-B1 Landing-day projection for bone, strength, aerobic capacity using NASA rates.
- FR-B2 `whatif(adherence)` returns updated projection; response curve labeled "assumption".
- FR-B3 UI text states "illustrative model, not a clinical predictor".

### FR-C Triage (Raghav) — see 07-TRIAGE_SPEC.md
- FR-C1 `TriageEngine.evaluate(day, telemetry, delaySec, options)` returns contract keys: `triageLevel`, `urgency`, `directGroundLinkRequired`, `rationale`, `flags`, `proposedAction`, `commDelaySeconds` (plus additive fields).
- FR-C2 Levels: SELF_TREAT, CREW_MEDICAL_OFFICER, FLIGHT_SURGEON. Urgency: ROUTINE, ELEVATED, CRITICAL_EMERGENCY.
- FR-C3 Emergency indicators (HR > 120, SBP > 160) set direct ground link regardless of link state.
- FR-C4 Vision symptoms trigger SANS monitoring with the exact wording "Report to the flight surgeon."
- FR-C5 Headache with CO2 ≥ 4500 ppm shows "Headache plus high CO2: check the scrubber first."
- FR-C6 Live link available and delay ≤ 10 s → flight surgeon live; otherwise onboard support → CMO; otherwise flight surgeon by packet.

### FR-D Packet and queue (Raghav)
- FR-D1 `PacketEngine.buildPacket` creates packet with ID `ARES6-MED-D<day>-<counter>`, timestamp, summary, trend, triage decision, priority, baseline summary, checksum.
- FR-D2 Checksum (FNV-1a over stable-stringified non-volatile fields) verified before acceptance; mismatch → permanent FAILED "Rejected: checksum mismatch."
- FR-D3 `QueueEngine` persists to localStorage; statuses QUEUED, TRANSMITTING, ACKNOWLEDGED, FAILED; link toggle; auto-retry up to 3 attempts; manual retry.
- FR-D4 In-flight packets return to QUEUED when link drops.

### FR-E UI (Om)
- FR-E1 Tabs: Monitor, Forecast, Act, Sources.
- FR-E2 Act tab shows triage card, packet preview, queue panel with status chips, link toggle, Retry button.
- FR-E3 Day slider/selector (Day 40 demo scenario), delay display.
- FR-E4 Sources tab: NASA figures vs assumptions, disclaimer.

## Non-functional requirements
- NFR-1 Offline: no network at runtime; fonts/Chart.js local.
- NFR-2 No build step; open `index.html` or serve statically.
- NFR-3 Deterministic output for the same input (testable).
- NFR-4 Performance: evaluate + build packet < 50 ms per render.
- NFR-5 Accessibility: color is never the only indicator; readable contrast; keyboard operable controls.
- NFR-6 Honesty: disclaimers visible; assumptions labeled.

## 6. Acceptance criteria (summary)
- AC1 Day 40 shows a drift alert with reasons and persistence ≥ 1.
- AC2 Forecast changes monotonically with adherence.
- AC3 Triage at Day 40 (≈128 s delay) yields CMO per contract example; flight surgeon when onboard support is off.
- AC4 Offline: disable network, app still works; link toggle off queues packets; link on delivers.
- AC5 Tampered packet is rejected as FAILED.
- AC6 `node triage/test_triage.js` → 40 passed, 0 failed.
